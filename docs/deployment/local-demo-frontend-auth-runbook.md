# Local Demo Frontend Authentication Runbook

This runbook describes a future, local-only integration between the frontend
development server and the isolated synthetic authentication service. It does
not change production login, legacy SMS OTP, the global Axios interceptor,
token storage, or the existing student/teacher routes.

## Review status and prerequisites

The frontend integration is proposed in [quranFront PR #26](https://github.com/AL-LMS/quranFront/pull/26).
The isolated backend implementation is proposed in [quranBack PR #74](https://github.com/AL-LMS/quranBack/pull/74).
Both are draft changes; check the current PR heads and review state before
using these instructions. The demo dashboard displays only a synthetic alias
and role. It does not provide real LMS courses, enrollment, quizzes, grading,
payment, or administrative actions.

Use a fresh backend worktree containing the local-demo-auth files and a
separate frontend worktree containing the PR #26 feature. Required local
tools are Docker Compose, Node/npm, Python 3.12 for backend dependency work,
and Docker CLI access from the Vite process. Do not use production or legacy
database URLs, real phone numbers, production credentials, or real accounts.

## Quarantined environment — do not restart or reuse

The prior Compose project `al-lms-local-04g-20261109` is quarantined after a
synthetic `teacher-01` credential was exposed. Do not start its containers,
authenticate against it, connect to its database, or reuse its credentials or
credential report. Preserve the volume
`al-lms-local-04g-20261109_db`; retiring it requires separate owner approval.

A future demo must use a new, unused Compose project, a newly created
database volume, and credentials generated by that fresh database's
initializer. Never copy the old account report. No instruction below starts
the quarantined project.

## Create a fresh backend demo

From the fresh backend worktree, first confirm that the selected project name,
its containers, network, and named volume are unused. Check that the fixed
loopback API port `18002` is free before starting services. Do not choose the
quarantined project name. Do not continue if the credential directory or
report already exists in this worktree; use a fresh worktree instead.

The commands below generate a new database password in the current shell and
never print its value. Keep shell tracing disabled. The initializer generates
five new synthetic account credentials in the ignored report.

```sh
cd /path/to/fresh/quranBack-worktree
set +x
export AL_LMS_LOCAL_DEMO_PROJECT="al-lms-local-auth-$(date -u +%Y%m%d%H%M%S)-$RANDOM"
export AL_LMS_LOCAL_DEMO_DB_PASSWORD="$(python -c 'import secrets; print(secrets.token_urlsafe(32))')"
export AL_LMS_LOCAL_DEMO_UID="$(id -u)"
export AL_LMS_LOCAL_DEMO_GID="$(id -g)"

test ! -e .local-demo-secrets
install -d -m 0700 .local-demo-secrets
test ! -e .local-demo-secrets/accounts.tsv

if test -n "$(docker ps -aq --filter "label=com.docker.compose.project=$AL_LMS_LOCAL_DEMO_PROJECT")"; then
  echo 'Compose project already exists; choose a different name.' >&2; exit 1
fi
if docker volume inspect "${AL_LMS_LOCAL_DEMO_PROJECT}_db" >/dev/null 2>&1; then
  echo 'Database volume already exists; choose a different name.' >&2; exit 1
fi
if docker network inspect "${AL_LMS_LOCAL_DEMO_PROJECT}_internal" >/dev/null 2>&1; then
  echo 'Network already exists; choose a different name.' >&2; exit 1
fi

docker compose -p "$AL_LMS_LOCAL_DEMO_PROJECT" -f compose.local-demo-auth.yml config --quiet
```

Review the rendered configuration without printing secret values. The
backend Compose definition uses PostgreSQL 16.6 on a project-specific
`internal: true` network, publishes no PostgreSQL port, and declares the API
mapping as `127.0.0.1:18002` to container port `8000`. This mapping is
loopback-only when the fresh Compose project is started; it is not a public
host bind. The previous 04G runtime used a different temporary configuration
and did not publish port 18002. Never infer that a port is currently active:
check the selected project's effective configuration and runtime mapping.

For an owner-approved local demo, start only the fresh project's services:

```sh
docker compose -p "$AL_LMS_LOCAL_DEMO_PROJECT" -f compose.local-demo-auth.yml up -d postgres
docker compose -p "$AL_LMS_LOCAL_DEMO_PROJECT" -f compose.local-demo-auth.yml run --rm initialize
docker compose -p "$AL_LMS_LOCAL_DEMO_PROJECT" -f compose.local-demo-auth.yml up -d auth-api
docker compose -p "$AL_LMS_LOCAL_DEMO_PROJECT" -f compose.local-demo-auth.yml ps
```

Verify project/service labels and health before using the API. The generated
account report is
`quranBack/.local-demo-secrets/accounts.tsv`; its directory must be mode
`0700` and the report mode `0600`. Read credentials privately from that file;
never put them in shell history, transcripts, screenshots, automation logs,
issues, or source code. The initializer will not overwrite an existing seed
or regenerate a missing report.

## Start the frontend and understand the proxy

Use a separate frontend terminal so the backend database password is not
inherited by `npm ci` or Vite. Copy only the non-secret project name selected
in the backend terminal. From the frontend PR #26 worktree, install the
locked Node dependencies and start Vite:

```sh
cd /path/to/quranFront-pr26-worktree
read -r -p 'Fresh backend Compose project name: ' AL_LMS_LOCAL_DEMO_COMPOSE_PROJECT
export AL_LMS_LOCAL_DEMO_COMPOSE_PROJECT
npm ci
VITE_ENABLE_LOCAL_DEMO_AUTH=true \
AL_LMS_LOCAL_DEMO_COMPOSE_PROJECT="$AL_LMS_LOCAL_DEMO_COMPOSE_PROJECT" \
npm run dev -- --host 127.0.0.1 --port 15173 --strictPort
```

Open <http://127.0.0.1:15173/local-demo/login>. The enabled Vite config
verifies a single healthy `auth-api` with the expected Compose project/service
labels on that project's internal network and discovers its current private
container IP at startup. Vite proxies only the local-demo API prefix to
container port `8000`; it does not hardcode an IP. The browser sends
same-origin requests to Vite and never connects directly to the Docker
network or the API host port. The API listens on `0.0.0.0:8000` inside its
container so the Vite host process can reach the private address. Docker's
loopback-only host mapping, when present, is separate from this proxy path.

The development server binds exclusively to `127.0.0.1:15173` when the
feature is enabled and fails if that port is occupied. Do not expose Vite on a
LAN or public interface. If service discovery, the network's `Internal`
property, health, or project labels cannot be verified, stop instead of
substituting a container IP, project, or database.

The demo routes are `/local-demo/login`, `/local-demo/otp`, and
`/local-demo/dashboard`. Login and OTP use a separate fetch client with
`credentials: "include"`; they do not use the production Axios interceptor or
production auth storage. The opaque session is an HttpOnly, SameSite=Strict
cookie. The frontend keeps the synthetic alias and role in memory only.

## Retrieve an OTP without exposing it

The Vite server returns `404` for the exact test-inbox path and encoded path
variants. The browser must never call the inbox. After the local OTP page
shows a challenge ID, retrieve the code only by `docker exec` into the
verified API container. Capture it without printing, then copy it to a local
clipboard using an approved clipboard tool. Keep shell tracing off; do not
redirect the response to a file or a transcript.

Example private-terminal procedure (the project variable must identify the
fresh project created above; this uses Docker labels directly and does not
need the backend password or Compose interpolation):

```sh
set +x
container="$(docker ps --filter "label=com.docker.compose.project=$AL_LMS_LOCAL_DEMO_COMPOSE_PROJECT" --filter 'label=com.docker.compose.service=auth-api' --format '{{.ID}}')"
test -n "$container"
test "$(printf '%s\n' "$container" | wc -l)" -eq 1
test "$(docker inspect --format '{{ index .Config.Labels "com.docker.compose.project" }} {{ index .Config.Labels "com.docker.compose.service" }}' "$container")" = "$AL_LMS_LOCAL_DEMO_COMPOSE_PROJECT auth-api"
read -r -s -p 'Challenge ID (hidden): ' challenge; printf '\n'
otp="$(printf '%s\n' "$challenge" | docker exec -i "$container" python -c '
import json, sys, urllib.request
challenge = sys.stdin.readline().strip()
url = "http://127.0.0.1:8000/api/local-demo/auth/v1/test-inbox/" + challenge
with urllib.request.urlopen(url, timeout=5) as response:
    sys.stdout.write(json.load(response)["code"])
' 2>/dev/null)"
unset challenge
if [[ ! "$otp" =~ ^[0-9]{6}$ ]]; then unset otp; echo 'OTP retrieval failed' >&2; exit 1; fi
if command -v wl-copy >/dev/null 2>&1; then
  printf '%s' "$otp" | wl-copy --trim-newline
elif command -v xclip >/dev/null 2>&1; then
  printf '%s' "$otp" | xclip -selection clipboard
else
  unset otp; echo 'Use a private clipboard tool; request a new challenge.' >&2; exit 1
fi
unset otp container
```

Paste the code into the browser before its five-minute expiry and clear the
clipboard afterward. The inbox entry is single-use. The backend also checks
that the request itself came from loopback inside the API container; the Vite
proxy filter is an additional browser boundary. No SMS or Kavenegar request is
made.

## Stop and dispose of only a new demo

Stop Vite with `Ctrl-C`. In the original private backend terminal (which has
the Compose-only variables in its environment), stop only the fresh backend
project's named services while preserving their state. Do not copy the
database password into the frontend terminal:

```sh
docker compose -p "$AL_LMS_LOCAL_DEMO_PROJECT" -f compose.local-demo-auth.yml stop auth-api postgres
```

If an owner later chooses to remove that newly created demo's containers and
network, re-verify the exact project label and volume name, then use
`docker compose ... down` **without** `--volumes`. This retains the named
database volume and credential report. Removing a project volume or report
requires a separate explicit decision after verifying ownership. Never use
`docker system prune`, wildcard names, or cleanup commands against another
project. The quarantined 04G project and its volume are outside every command
in this runbook.

## Production and feature boundaries

- The local-demo route is registered only when Vite development mode and
  `VITE_ENABLE_LOCAL_DEMO_AUTH=true` are both present. The production Vite
  build does not register or bundle the local-demo route chunk, even if the
  flag is supplied during a build.
- The Vite Docker-discovery proxy is development-only. It requires a unique
  project with a healthy API on its private internal network.
- The inbox is not proxied to the browser. Direct host/API access is not the
  frontend integration path.
- This is a synthetic demonstration, not an identity provider, authorization
  system, or production login. It grants no real course access and provides
  no real student, teacher, or administrator workflow.
- The previous 04G service and volume remain quarantined and retained. A fresh
  project and newly generated credentials are mandatory.
